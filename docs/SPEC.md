## 1. Product in one paragraph

A brand posts a deal (for example "3 Instagram posts for ₹10,000"). Creators apply. The brand confirms one creator. The brand pays ValueSkins' commission (₹885). The brand pays the creator a 30% advance (₹2,734.50), paid directly by UPI to the creator and confirmed by the creator. The creator uploads the content as a Google Drive link. The brand requests changes or approves. The brand pays the remaining 70% (₹6,380.50), paid directly by UPI to the creator and confirmed by the creator. Both parties get a Deal Report (ADP) PDF with all invoices and proof of delivery. The brand's total is exactly the budget. No chat, no negotiation.

## 3. Core constraints (the product rules)

1. One brand and one creator per deal. No multi-creator deals, no creator-creator collabs.
2. Real-time deal feed: new deals appear for creators instantly over WebSocket.
3. No niches, no categories, no filtering. All open deals are visible to all creators.
4. No negotiation. The budget is final.
5. No chat. The only brand-to-creator text is revision feedback.
6. The ValueSkins fee goes brand -> Razorpay -> ValueSkins. The creator's share is paid by the brand directly to the creator's UPI ID and never passes through ValueSkins (REPLACEMENT_PLAN 2.1).
7. Account type (Creator or Brand) is chosen once at onboarding and is locked.
8. Instagram is the profile. It is fetched automatically and refreshed daily.
9. Creators save their UPI ID and the name on the account once. Brands set up billing details once.
10. A verified email is required before using the marketplace.
11. The virtual resume is visible on hover over any user, everywhere.
12. Everyone is equal: no tiers, no levels, no badges.
13. No length limits on deal descriptions.
14. Deal communication happens by email, and every email about a deal is visible to both parties on the deal page.
15. No phone numbers shown or used for communication. (See 7.2 about Razorpay possibly requiring one for KYC.)
16. Web app only, responsive for desktop and tablet, usable on mobile browsers.
17. The fee (commission) is non-refundable once paid.
18. After the fee is paid, neither party can cancel. Only an admin can, through a dispute.
19. Plain black UI. No gradients, no shadows, no emojis, no em dashes, no marketing language.

## 4. Money

### 4.1 Rules

- All amounts are stored and computed as **integer paise** (`BIGINT` in Postgres, `number` in TS, validated as safe integers). Never floats.
- Brands enter the budget in **whole rupees**. The server converts it to paise.
- All money math lives in `packages/shared/src/money.ts`. Nothing else computes amounts.
- The breakdown is computed **once, at publish**, and frozen on the deal row. Later config changes never affect published deals.

### 4.2 Formula

Config (in `packages/shared/src/config.ts`):

```
MIN_BUDGET_PAISE          = 886_00       // ₹886: above the fee including GST (a test checks this)
COMMISSION_FLAT_PAISE     = 750_00       // ₹750
COMMISSION_PERCENT_BPS    = 0            // no percentage: the fee is flat (REPLACEMENT_PLAN 2.2)
GST_RATE_BPS              = 1800         // 18%
ADVANCE_PERCENT           = 30
```

Computation:

```
commission_base  = max(COMMISSION_FLAT_PAISE, round_half_up(budget * COMMISSION_PERCENT_BPS / 10000))
commission_gst   = round_half_up(commission_base * GST_RATE_BPS / 10000)
commission_total = commission_base + commission_gst
creator_amount   = budget - commission_total
advance          = round_half_up(creator_amount * ADVANCE_PERCENT / 100)
final            = creator_amount - advance
```

Invariant (tested): `commission_total + advance + final == budget`, all positive.

Worked example, budget ₹10,000 (1,000,000 paise):

| Item                         | Paise     | Rupees    |
| ---------------------------- | --------- | --------- |
| Commission base              | 75,000    | 750.00    |
| GST 18%                      | 13,500    | 135.00    |
| Commission total (Payment 1) | 88,500    | 885.00    |
| Creator amount               | 911,500   | 9,115.00  |
| Advance 30% (Payment 2)      | 273,450   | 2,734.50  |
| Final 70% (Payment 3)        | 638,050   | 6,380.50  |
| Brand pays in total          | 1,000,000 | 10,000.00 |

Worked example, budget ₹50,000: commission base ₹750, GST ₹135, total ₹885, creator ₹49,115, advance ₹14,734.50, final ₹34,380.50. The fee is ₹885 at every budget; only the creator's share grows.

Worked example, the minimum budget ₹886 (88,600 paise): fee ₹885.00 (base ₹750, GST ₹135), creator amount ₹1.00, advance 30% = ₹0.30 (30 paise), final ₹0.70 (70 paise). Fee 88,500 + 30 + 70 = 88,600. The minimum is the smallest whole-rupee budget above the fee, so the creator's share is always positive. The UPI link for these amounts carries `am=0.30` and `am=0.70` (`paiseToDecimalString`). `MIN_BUDGET_PAISE` has a test that it stays above `COMMISSION_FLAT_PAISE` plus GST at `GST_RATE_BPS`, so a later fee change cannot slip under it. `GET /api/config` returns it as `minBudgetPaise`; the web reads it from there.

`computeBreakdown` takes the GST rate as an optional parameter (basis points), defaulting to `GST_RATE_BPS` above. The API passes its `GST_RATE_BPS` env var, which defaults to `1800`. GST is charged (REPLACEMENT_PLAN 2.2), so a startup guard refuses to start when it is above 0 and `COMPANY_GSTIN` is empty. A deal keeps the breakdown frozen when it was published, whatever the rate is later.

Worked example at GST 0 (a test environment, no GST): budget ₹10,000: commission base ₹750, GST ₹0, total ₹750, creator ₹9,250, advance ₹2,775, final ₹6,475.

### 4.3 Razorpay fees

ValueSkins absorbs Razorpay's fees. They are never shown to or charged to users, except as an informational line in the ADP.

**Closed (Prompt 13).** Razorpay now charges a fee only on ValueSkins' commission. The advance and final are paid directly by the brand to the creator's UPI ID (section 7.3), so there is no Route transfer, no platform float and no gateway fee to add to what the brand pays. The brand's total is exactly the budget.

## 5. Deal lifecycle

### 5.1 Statuses

`DRAFT, OPEN, CONFIRMED, COMMISSION_PAID, ADVANCE_PAID, CONTENT_UPLOADED, REVISION_REQUESTED, APPROVED, COMPLETED, CANCELLED`

Derived flags (not statuses):

- `applications_open` = `status == OPEN && now < end_of_day_IST(application_deadline)`
- `content_overdue` = `status in (ADVANCE_PAID, REVISION_REQUESTED) && now > end_of_day_IST(content_upload_deadline)`

### 5.2 Transitions (the only allowed ones)

| From                                                                          | To                 | Who     | Trigger                                                                                                                                                                                                                                                                                                                                                                        |

Everything else is rejected with `409 INVALID_TRANSITION`. Creators cannot cancel at any stage. A brand can cancel free until it pays the fee (OPEN and CONFIRMED). From COMMISSION_PAID to APPROVED the brand's cancel answers `409 CANCELLATION_NOT_POSSIBLE` and its CANCEL action is disabled with "The deal cannot be cancelled after the fee is paid. Write to us if something is wrong." The table has 16 rows.

### 5.3 How transitions are implemented

- One function, `transitionDeal({ dealId, from, to, actor, patch, note, metadata, prepare, within, afterCommit })`, in `apps/api/src/deals/stateMachine.ts`. Nothing else writes `deals.status`; a test fails if another file updates the deals table.
- It first checks the pair and the actor role against the table in `packages/shared` (`409 INVALID_TRANSITION`), then runs a single DB transaction: `UPDATE deals SET status = :to, ... WHERE id = :id AND status = :from RETURNING *`. Zero rows means someone else changed it first, so it returns `409 INVALID_TRANSITION`.
- The same transaction inserts a `deal_events` row (from, to, actor, note).
- `prepare(tx, deal)` runs first, on the row locked with `SELECT ... FOR UPDATE`, and returns more columns to set (publish validates the draft again and computes the money breakdown there, so an edit racing the publish cannot slip past). `within(tx, deal)` runs after the status update in the same transaction; if it throws, the whole transition rolls back (confirm uses it to confirm the application, reject the others and set `creator_id`).
- After commit, it runs the `afterCommit` list in order: emails now, WebSocket events when Socket.io exists (section 10). Side effects never run inside the transaction, and a failing task is logged and never fails the request or stops the next task.
- The allowed-transition table lives in `packages/shared` and is covered by exhaustive tests.

### 5.4 Deadlines

- Three dates: `application_deadline < content_upload_deadline <= deal_deadline`. All must be in the future at publish time: the end of that day in IST must be after now, so today's date is allowed until 23:59:59 IST.
- Dates are calendar dates interpreted in IST. A deadline means 23:59:59 IST on that date.
- After the application deadline, Apply is disabled with the message "Applications closed". The brand can still confirm an existing applicant.

### 5.5 Phases (user-facing)

1. **Brand posts deal.** Form: title, description (with template, see section 9), budget in rupees, the three deadlines. Brand sees the full payment breakdown before publishing. Publish sets status OPEN, broadcasts `deal:new` to all connected creators, sends Email 1.
2. **Creators apply.** Feed shows brand name (hover for virtual resume), budget, creator amount, deadlines, description. Apply needs a saved UPI ID, name and consent (`403 PAYOUT_NOT_SET`). If it is missing, the button reads "Add your UPI ID to apply" and links to settings.
3. **Brand confirms a creator.** Application list with hover resumes. Confirm on one creator, and the rest are auto-rejected.
4. **Payment 1, the ValueSkins fee.** "Pay ValueSkins fee: ₹885.00" (`payFeeLabel` in `copy.ts`). Razorpay Checkout. On capture: COMMISSION_PAID, invoice issued (a tax invoice when GST is charged), Email 4 with it attached. Users see "ValueSkins fee" everywhere (copy, email subjects and bodies, PDFs, error messages); identifiers, enums, table names and URL slugs keep "commission".
5. **Payment 2, advance, paid directly.** "Pay advance: ₹2,734.50". The brand pays the creator's UPI ID outside ValueSkins (a `upi://pay` link and QR code from `GET /deals/:id/direct-payment`) and records the UPI reference (`POST /deals/:id/direct-payment`); recording does not move the deal. The creator gets Email 17, checks their UPI app and confirms (`POST /direct-payments/:id/confirm`): ADVANCE_PAID, Email 5 to both with the payment record attached. If the money did not arrive the creator says so (`POST /direct-payments/:id/not-received`, Email 18 to both, alert A1 to the admin): the record is kept, marked not received, and the brand records again.
6. **Creator uploads content.** Countdown to the upload deadline. Paste a Google Drive link (validated as `https://drive.google.com/...` or `https://docs.google.com/...`). CONTENT_UPLOADED, Email 6. Every link is kept in `content_uploads`, so a re-upload never erases the earlier ones; at most 20 links per deal. Uploading after the deadline is allowed (the deal is only flagged overdue).
7. **Brand reviews.** Either "Suggest changes" (text, REVISION_REQUESTED, Email 7) or "Final approval" (APPROVED, Email 8). After 5 revisions, both see: "This deal has had 5 revisions. If you cannot agree, raise a dispute." The feedback text and its time are kept as the note of the deal event, and each round adds one to `revision_count`.
8. **Payment 3, final, paid directly.** "Pay final: ₹6,380.50". The same flow as the advance. When the creator confirms: COMPLETED, Email 9 with the payment record attached, then the deal record is ready, Email 10.
9. **Deal record (ADP).** Downloadable by both parties from the deal page at any time after completion, and attached to Email 10. Generated on demand.

**Whose turn it is** (`computeDealTurn` in `packages/shared/src/dealTurn.ts`, used by `GET /deals/mine`; a test keeps it in step with `allowedActions`). `nextStep` is the same for both parties, and `yourTurn` is true when the actor is the caller's role. A turn that is blocked (a creator with no UPI ID, a full upload list) is still that person's turn: the deal page shows the reason.

| DRAFT                            | `PUBLISH`                                                     | Brand          |

## 6. Authentication and onboarding

### 6.1 Instagram login

- Product: **Instagram API with Instagram Login** (Business Login for Instagram), host `graph.instagram.com`, scope `instagram_business_basic`.
- Only public Instagram **Business** and **Creator** accounts can sign in, and the **role comes from the account type at every sign-in**: `BUSINESS` is a brand and `MEDIA_CREATOR` is a creator (`roleFromAccountType` in `packages/shared`). Any other type, or none, stops the sign-in with: "ValueSkins needs a public Instagram Business or Creator account. A Business account posts deals as a brand. A Creator account applies to deals." (redirect code `account_type_unsupported`). Meta's docs list the values as Business and Media_Creator; the API sends them in capitals and the mapping ignores case.
- The type is stored (`users.ig_account_type`). A returning account follows a changed type only if it has no deals as a brand, and no deals or applications as a creator (a draft counts); the check and the change run in one transaction with the user row locked, so a deal cannot be created in between. Otherwise sign-in is refused with `409 ACCOUNT_TYPE_CHANGE_BLOCKED`, which names the support address (redirect code `account_type_change_blocked`), and nothing changes. When the type does change, the saved profile details start again, because they are for the old role. Link mode follows the same rules, and is how an email-only account gets its role.
- Flow:
  1. Web "Continue with Instagram" goes to `GET https://api.valueskins.com/api/auth/instagram/start`. The API sets a signed `state` cookie and redirects to Instagram's authorize URL.
  2. Instagram redirects to `GET /api/auth/instagram/callback?code&state`. The API verifies state, exchanges the code for a short-lived token, exchanges that for a long-lived token (about 60 days), and fetches the profile.
  3. Upsert the user by Instagram user id, with the role from the account type (above). Create a session. Redirect to `https://valueskins.com/onboarding` if onboarding is incomplete, else `/home`.
- **Link mode**: `GET /api/auth/instagram/start?link=1` (must already be logged in) attaches the fetched Instagram account to the current user instead of creating a session, and redirects to `/home` on success. If that Instagram account already belongs to a different user, nothing is mutated and the browser is redirected with an error instead.
- **On the web** (section 18): a failed sign-in lands on `WEB_ORIGIN/login?error=<code>`, which shows the matching error page; `/home` sends each person to their own start page or to `/onboarding`. The codes: `instagram_failed`, `state_invalid`, `must_be_logged_in`, `account_linked_elsewhere` (sent to `/settings`), `account_type_unsupported`, `account_type_change_blocked`, and `instagram_account_rejected`.
- **Failures in the callback.** Each call to Meta is a named step: `code_exchange`, `long_lived_exchange`, `profile`, `media`. A failure is logged with its step, Meta's error number, type, subcode and `fbtrace_id`, and the HTTP status, never a token, the sign-in code or a secret. When the code exchange worked but the long-lived exchange or the profile answers Meta error code 100 ("Unsupported request"), the redirect code is `instagram_account_rejected`: Instagram signed someone in but will not serve that account, which in practice is the wrong account, or a personal one, in that browser's Instagram session. Every other failure is `instagram_failed`.
- Profile fields fetched from `/me`: `user_id, username, name, account_type, profile_picture_url, followers_count, follows_count, media_count, biography`. Verify the exact field list against Meta's docs at build time. If `biography` is not available on `/me`, drop it.
- Engagement rate = average of (likes + comments) over the latest 12 media, divided by followers, as a percentage with 2 decimals. Null if fewer than 3 posts or 0 followers.
- The long-lived token is stored **encrypted** (AES-256-GCM, key from env `TOKEN_ENCRYPTION_KEY`). It is renewed by the daily `instagram-refresh` job when it has less than 10 days left (section 14).
- Profile is refreshed on every login and by the daily `instagram-refresh` job (section 14). The name is the Instagram name only until the user's profile is locked (section 6.4); after that it is the name the user gave. `is_admin` is recomputed from `ADMIN_INSTAGRAM_USER_IDS` on every login/upsert, in both directions.
- Meta app requirements, built into the product: `/privacy` and `/terms` pages on the web app, a **data deletion callback** (`POST /api/meta/data-deletion`, returns a confirmation code and status URL, `GET /api/meta/deletion-status/:code` to check it) and a **deauthorize callback** (`POST /api/meta/deauthorize`). Both verify Meta's `signed_request` with `META_APP_SECRET`. Deauthorize only clears the now-invalid stored token (`ig_token_encrypted`, `ig_token_expires_at`) for that Instagram user id — it does not delete the account; full soft-delete and anonymization (section 15) is exclusive to data-deletion and `DELETE /me`.

### 6.2 Dev login (non-production only)

Meta app review takes weeks, and building cannot wait. In development and staging, `POST /api/dev/login` accepts `{ username, role, admin? }` and creates or logs in a fake user with fake Instagram data (the account type is set to match the role, `BUSINESS` or `MEDIA_CREATOR`; the role is a dev-only shortcut and never comes from a request in production). `admin: true` makes the new user an admin, so the admin screens can be checked without an Instagram account in `ADMIN_INSTAGRAM_USER_IDS`. Like the role, it applies only when the user is created, never to an existing one. It is registered only when `NODE_ENV !== 'production'` **and** `ENABLE_DEV_LOGIN=true`, and the handler itself answers 404 in production as a second guard. A startup check crashes the process if both `NODE_ENV=production` and `ENABLE_DEV_LOGIN=true` are set. A test proves that no user, and no admin, can be created this way in production.

### 6.3 Sessions and security

- Session = random 32-byte token in an httpOnly, Secure, `SameSite=Lax` cookie with `Domain=.valueskins.com`. Only its SHA-256 hash is stored in `sessions`. 30-day expiry, sliding.
- Every mutating request must carry an `Origin` header equal to `WEB_ORIGIN` (`https://valueskins.com` in production), checked server side as CSRF protection, in addition to SameSite. Webhook and Meta callback routes are exempt (they verify signatures instead).
- Logout deletes the session row.
- Socket.io authenticates with the same cookie during the handshake (section 10).

### 6.4 Onboarding (all steps required, in order)

1. **Instagram profile.** Show the fetched Instagram data. "Is this you?" There is no account type question: the role comes from the Instagram account type (section 6.1).
2. **Email.** Required. The server sends a verification link (token valid 24 hours, single use, only the hash stored). The user must click it before continuing; the link works in any browser, signed in or not. Changing email later re-runs verification. "Send the link again" waits 60 seconds after a send, with a visible countdown.
3. **Profile details, saved once and then locked** (`PUT /me/profile`). The fields depend on the role of the session, never on the request. Before the save, the web lists the values in a confirm ("Save your profile?", "Check again" or "Yes, save it"), because they cannot be changed afterwards.
   - Creators: name, city, age (18 to 99) and gender (`MALE`, `FEMALE`, `OTHER`, `PREFER_NOT_TO_SAY`).
   - Brands: name, city, website (`http://` or `https://`, up to 200 characters) and an optional hiring pitch (up to 1,000 characters).
   - Both tick "I am 18 or older" (`adultConfirmed: true`), stored as `adult_confirmed_at`. Names and cities are 2 to 100 characters; a name uses letters, spaces, dots, hyphens and apostrophes. Bodies are strict: a field for the other role is rejected.
4. **Type-specific setup.**
   - Creator: **UPI payout details** (section 7.2). Creators may browse deals before finishing, but cannot apply until they have saved a UPI ID, the name on the account and consent.
   - Brand: **Billing details**: billing name, billing state (for GST place of supply), billing address, GSTIN (optional, validated format). Required before publishing a deal.
5. **Marketplace.**

Which steps apply, which are done and which is next is returned by `GET /me` as `onboarding` (`{ completed, nextStep, steps: [{ id, done, required }] }`, step ids `instagram`, `email`, `profile`, `billing`, `payout`), computed by `computeOnboarding` in `packages/shared`. `GET /me` also returns `profileDetails` (the locked details with the current age, or null before they are saved). Marketplace is UI-only and not tracked.

- **Completion.** `onboarding_completed_at` is set, once and never unset, when Instagram is connected, the email is verified, the profile is saved, plus billing details for a brand. The UPI payout step is not required to complete: creators may browse before finishing it. It is done when the UPI ID, name and consent are all saved, and it gates applying and being confirmed, not onboarding.
- **Email-only accounts** (staging and tests, section 6.5) have no role, so they see only the Instagram and email steps and cannot finish until they connect Instagram (`GET /auth/instagram/start?link=1`, which also gives them their role). Until then every role-gated route answers `403 INSTAGRAM_NOT_CONNECTED` ("Connect your Instagram account to continue.").
- **Profile** (`PUT /me/profile`): once only, by one conditional `UPDATE ... WHERE profile_locked_at IS NULL`, so two racing requests cannot both win. A second save answers `409 PROFILE_LOCKED`, naming `SUPPORT_EMAIL`: corrections go to support by email, who fix the row by hand. It saves the age and the time it was given (`age`, `age_recorded_at`); the **current age** is the age plus the whole years since, worked out on read (`currentAge` in `packages/shared`) and never stored. `users.name` becomes the name given, and Instagram sign-in stops overwriting it. Followers and engagement still come from Instagram and refresh on sign-in. Rate limited (section 13). Users who finished onboarding before Prompt 14 keep their completion and may save the profile later; nothing is gated on it yet.
- **Email for Instagram accounts** (`POST /me/email`, `/me/email/verify`, `/me/email/resend`). `users.email` changes only when the new address is verified, so a changed address leaves the old verified one in place until then. The link is `WEB_ORIGIN/verify-email?token=...`, valid 24 hours, single use, only the hash stored; every bad token (unknown, expired, used) is the same `400 INVALID_TOKEN`. `POST /me/email/verify` needs no session: the token alone proves the address and decides which user is verified, never the session, because mail apps often open links in their own browser. It never creates a session or sets a cookie. It answers `{ verified, email, onboarding }`, where `onboarding` is that user's state only when the request is signed in as that same user, and null otherwise. The web page calls it once, whether or not the visitor is signed in; signed out (or signed in as someone else) it shows "Email confirmed" and "Go back to the browser where you started, or sign in here with the same Instagram account." with Sign in with Instagram. `POST /me/email` always answers 200 whether or not another account uses the address; a clash is reported at verify time as `409 EMAIL_TAKEN`. Email-only accounts cannot use these routes (`409 EMAIL_IS_SIGN_IN`): their email is their sign-in. Resend is rate limited (section 13).
- **Brand billing** (`PUT /me/billing`, `GET /me/billing`): brands only (`403` for anyone else), GSTIN format-validated. `GET` answers `200 { billing }` with `{ billingName, billingAddress, billingState, gstin }` (`gstin` null when none), or `{ billing: null }` before anything is saved; `PUT` returns the same `billing` object. Only the signed-in brand's own details are ever returned.
- **Pending email and adult confirmation on `GET /me`.** `user.pendingEmail` is the address the last verification link went to, while that link is unused and unexpired and the address is not already the verified one, else null; only the signed-in user's own. `profileDetails.adultConfirmedAt` is when the user ticked "I am 18 or older" (saved with the profile).
- **Profile on `GET /me`.** `profile` also carries `biography` (the Instagram bio) and `accountType` (the Instagram account type as stored, for example `BUSINESS` or `MEDIA_CREATOR`); both are null for an account with no Instagram data, such as an email-only account.

### 6.5 Email login (staging and tests only)

Production sign-in is **Instagram only** (REPLACEMENT_PLAN 2.3): `AUTH_EMAIL_ENABLED` is `false` in production, and a startup guard refuses to start with `NODE_ENV=production` and `AUTH_EMAIL_ENABLED=true`. On staging and in tests it enables an email-code login path alongside Instagram login. Codes are tracked in `email_login_codes` (section 15); a user created this way has `instagram_user_id`, `ig_account_type`, `ig_token_encrypted` and `ig_token_expires_at` all null until they later link Instagram.

- `POST /auth/email/start { email }`: always responds `200 { ok: true }`, regardless of whether an account exists for that email — this is the whole non-enumeration mechanism, not a special case on top of it. Generates a 6-digit numeric code, invalidates any prior unused code for that email, and sends it with the "Your sign-in code" template. Valid for 10 minutes. Rate limited as a login attempt (section 13).
- `POST /auth/email/verify { email, code }`: on a correct, unexpired, unused code with fewer than 5 prior wrong attempts on it, marks the code used, finds the user by email or creates one (`email_verified_at` set immediately), and creates a session. Every failure (no code, wrong code, expired, 5 attempts already used) returns the identical `400 INVALID_CODE` — never distinguished. Also rate limited as a login attempt.
- A brand-new email-only user has no Instagram handle to derive a username from; `username` and `name` default to the email's local-part. It has no role until it connects Instagram (section 6.4).
- On the web, the home page shows "Sign in with email" (to `/signin/email`) only while `GET /api/config` returns `authEmailEnabled: true`; `/signin/email` is the 404 page otherwise.

## 7. Razorpay

### 7.1 Modes and keys

- `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` come from env.
- Local and staging use **test keys**. Production uses live keys. The API logs the mode (`test` or `live`) at startup, and refuses to start if `NODE_ENV=production` with a test key, or non-production with a live key.
- Route is not used (REPLACEMENT_PLAN 0). Only the commission is paid through Razorpay.
- **Payments can be off** (`PAYMENTS_MODE`, section 19). While it is `off` the three Razorpay variables are optional, and the key-mode check above runs only when `RAZORPAY_KEY_ID` is set. In production, any mode other than `off` needs a live key id, the key secret, the webhook secret and `COMPANY_GSTIN`, or the API refuses to start. The startup log shows the Razorpay mode (`none` when there is no key) and both launch modes.

### 7.2 Creator payout details (UPI)

Replaces the Route linked-account setup (REPLACEMENT_PLAN 2.1). Nothing is sent to Razorpay.

- **Fields:** the UPI ID (`vpa`), the name on the account as the creator's UPI app shows it (`name`), and consent. Body of `PUT /me/payout-upi`: `{ vpa, name, consent: true }`, unknown fields rejected.
- **UPI ID format:** `^[a-zA-Z0-9.\-_]{2,64}@[a-zA-Z]{2,32}$`, trimmed and stored in lower case. Enforced by the Zod schema and by a database CHECK (`users_payout_vpa_check`). Anything shaped like a bank account number (9 to 18 digits), a PAN or an IFSC code is refused with a message that says so; the same shapes are refused as the name. Messages never repeat what was typed.
- **Name:** 2 to 80 characters, letters in any script, spaces, dots, hyphens and apostrophes.
- **Consent:** "I agree my UPI ID and name are shown to a brand that confirms me on a deal." Saving stamps `payout_vpa_consent_at`; saving again replaces everything. The page also says: "We do not verify UPI IDs. Enter yours carefully. A payment to a wrong UPI ID cannot be recalled."
- **Storage:** `users.payout_vpa`, `payout_name`, `payout_vpa_consent_at`. Never PAN, bank account numbers or IFSC. Account deletion clears all three.
- **Disclosure:** the full UPI ID goes only to the brand confirmed on a deal, only when the creator consented and only while a direct payment is due (`GET /deals/:id/direct-payment`, section 7.3a). Everywhere else, including the creator's own settings, it is masked: `cr•••@okhdfcbank` (the first two characters before the @, or one if there are only two). `GET /me/payout-upi` answers `{ payoutUpi: { maskedVpa, name, consentAt } | null }`. It is never logged: the logger redacts UPI-shaped values and the keys `vpa`, `upi` and `payout`.
- **Endpoints:** `PUT /me/payout-upi` (creators only, 10 saves per hour per user) answers `{ payoutUpi, onboarding }`; `GET /me/payout-upi` (creators only).
- **Gating:** applying needs all three (`403 PAYOUT_NOT_SET`, "Add your UPI ID to apply"); confirming an applicant needs them still saved (`409 CREATOR_PAYOUT_NOT_SET`).

### 7.3 Payments

- For the commission, the server creates a Razorpay Order: amount from the frozen breakdown, `currency: INR`, `receipt` = `<dealShortId>-<type>` (`commission` is the only type), notes `{ deal_id, type }`. Capture is automatic through the Razorpay account setting (the Orders API takes no per-order flag).
- **The advance and final are not Razorpay payments.** They are direct brand-to-creator UPI payments (section 7.3a). `POST /deals/:id/payments/:type/order` accepts only `commission`; any other type is `400 VALIDATION_ERROR`.
- Only one open Order per deal per deal for the commission (a partial unique index enforces it, and a lock stops two simultaneous requests creating two). If one exists and is unpaid, it is reused. A declined attempt does not close the order: `payment.failed` marks the payment FAILED with Razorpay's reason and leaves the deal untouched, and the next order request reuses the same Razorpay order and reopens it (CREATED). A late successful capture is accepted from CREATED or FAILED.
- **While payments are closed for the caller** (section 19), the order endpoint answers `503 PAYMENTS_NOT_OPEN`, "Payments open soon. We will email you when they do.", before it calls Razorpay or writes a payment. It comes after the ownership check (anyone else gets 404) and before the status check. `POST /payments/verify` is not gated: it needs a signed Razorpay order, and it shares `markPaymentCaptured` with the webhook, so a payment already taken is never stranded.
- The endpoint checks: the caller is the deal's brand (anyone else gets 404), and the deal is in the correct status (CONFIRMED; otherwise `409 WRONG_DEAL_STATUS`, "The ValueSkins fee is not due on this deal", with no raw status in the message).
- Frontend opens Razorpay Checkout with the Order id and the order's `keyId`. On the Checkout success handler it calls `POST /api/payments/verify` with `razorpay_order_id, razorpay_payment_id, razorpay_signature`. The server verifies the signature.
- **Both** the verify endpoint and the webhook call the same idempotent function `markPaymentCaptured(orderId, paymentId)`. Whichever arrives first performs the transition. The second is a no-op. It does not trust the browser or the webhook body: it fetches the payment from Razorpay and requires status `captured`, the same order, the order's amount and `INR`; a mismatch records nothing, answers `409 PAYMENT_AMOUNT_MISMATCH` (or `PAYMENT_ORDER_MISMATCH`, `PAYMENT_NOT_CAPTURED`) and alerts the admin (A1). The answer's message is plain words (`PAYMENT_COULD_NOT_BE_CONFIRMED`, `PAYMENT_NOT_CONFIRMED_YET` in `copy.ts`); the technical detail (ids, amounts, Razorpay's status) goes only to the alert and the webhook event row. In one transaction it marks the payment CAPTURED, issues the commission invoice and transitions the deal with a SYSTEM actor (CONFIRMED to COMMISSION_PAID). Email 4 goes out after commit, with the invoice attached (section 7.4). **A fee captured on a deal that changed.** If the deal is no longer CONFIRMED when the fee is captured (for example the brand cancelled while Checkout was open):
  - the payment is kept as CAPTURED, with no invoice, and the deal does not move
  - a deal event of kind `FEE_CAPTURED_DEAL_CHANGED` (actor SYSTEM, the payment id in its metadata) is written in the same transaction
  - after the commit, and only by the caller that recorded it, the admin gets alert A1, "Fee received on a deal that had changed, refund by hand", and the brand gets email 21 ("Your payment of ₹885.00 went through, but the deal had already changed. We will refund it."). `deal:updated` and `deal:summary` go out.
  - `POST /payments/verify` answers `409 FEE_CAPTURED_DEAL_CHANGED` with that message whenever the event exists, so verify first, the webhook first, both repeated or both at once give one event, one alert, one email and the same answer. The webhook answers 200.
  - The refund is done by hand in Razorpay.
  - A second captured fee for a deal that already has one cannot be stored as CAPTURED (one captured fee per deal), so it is marked FAILED for refund, with the duplicate alert. To the brand it is the same case: the same event, email 21 and verify answer, once.
- `POST /payments/verify` checks the Checkout signature (HMAC-SHA256 of `order_id|payment_id` with the key secret, constant-time compare, `400 INVALID_SIGNATURE`), then calls `markPaymentCaptured`. Only the deal's brand can verify its payments.
- Webhook endpoint `POST /api/webhooks/razorpay`:
  - While `PAYMENTS_MODE=off` it answers `404 NOT_FOUND` to everything, before the signature check, and stores nothing. In `admins` and `on` it works as below. Set `off` only when no fee order is open: Razorpay does not retry a 404 for long.
  - Uses the raw body for HMAC-SHA256 signature verification with the webhook secret. Invalid signature returns 400.
  - Deduplicates on the `x-razorpay-event-id` header, stored in `webhook_events`. Duplicates return 200 immediately.
  - Handles, by a registry keyed by event type: `payment.captured`, `order.paid` (both call `markPaymentCaptured`) and `payment.failed`. An event with no handler (for example `settlement.processed`, or an old `transfer.*` or `product.route.*`) is stored and marked processed.
  - Always returns 200 quickly after storing the event: the event is processed after the response. The stored payload is redacted (PAN, KYC, phone and legal info removed, account numbers reduced to their last 4 digits, and the payer's email, contact, VPA, card, bank and wallet details removed). Processing errors are recorded on the event row (the message, never the payload) and alerted to the admin (template A1, sent to `DISPUTE_EMAIL`), never retried in a loop.

### 7.3a Direct payments (advance and final)

REPLACEMENT_PLAN 2.1. The brand pays the creator's UPI ID itself; ValueSkins never receives or holds that money. A `direct_payments` row records each attempt and is never edited or deleted once it is confirmed or disputed (a correction is a new row).

- **What to pay** (`GET /deals/:id/direct-payment`, the deal's brand only, `Cache-Control: no-store`): the stage due (the advance in COMMISSION_PAID, the final in APPROVED), the amount from the frozen breakdown, the creator's full UPI ID and name, the `upi://pay` fields (`pa`, `pn`, `am` with two decimals built with integer math, `cu=INR`, `tn` = `ValueSkins <shortId> advance|final`) and the ready link. This is the only response that carries the full UPI ID, and only while a stage is due and the creator has saved all three payout details. Otherwise `blocked` is `no_creator`, `not_due`, `creator_has_no_upi` or `no_consent` and nothing about the creator comes back. While a record waits for the creator, `record` shows it and the details stay visible.
- **Record** (`POST /deals/:id/direct-payment`, the deal's brand, body `{ stage, reference, note? }`): the reference is 6 to 40 characters from `A-Z a-z 0-9 - /`; the note is optional (500). The stage must be the one due (`409 WRONG_DEAL_STATUS`, "The advance payment is not due yet" or "The final payment is not due yet"), the creator must have details (`409 CREATOR_PAYOUT_NOT_SET`, with the reason "The creator has not added a UPI ID yet" or "The creator has not agreed to share their UPI ID", never a message about confirming a creator). The record and its deal event (see section 15) are written in one transaction, so a failure leaves neither. The amount is the frozen one; a client amount is rejected. The row snapshots the creator's UPI ID in `paid_to_vpa` and the amount. A partial unique index allows one live (not disputed) record per deal and stage, so a second record while one waits is `409 DIRECT_PAYMENT_ALREADY_RECORDED`. Recording never changes the deal status. Email 17 goes to the creator. 10 per hour per brand.
- **Confirm** (`POST /direct-payments/:id/confirm`, the deal's confirmed creator only; the brand, other creators and admins cannot): one `transitionDeal` with a CREATOR actor (COMMISSION_PAID to ADVANCE_PAID, or APPROVED to COMPLETED, with `advance_paid_at` or `completed_at`) in the same transaction as the record's confirmation and the payment record document (section 7.4). Two confirms at once: one wins, the other is `409`. A deal cancelled in the meantime answers `409 INVALID_TRANSITION`. Emails 5 or 9 go to both with the payment record attached; on the final, email 10 follows. 20 an hour per creator, shared with not received.
- **Not received** (`POST /direct-payments/:id/not-received`, the confirmed creator, body `{ reason }`): marks the record disputed (`disputed_at`, `dispute_reason`). The deal does not move. The lock on the deal, the update of the record and the deal event (`PAYMENT_NOT_RECEIVED`, the creator's reason as its note) are one transaction. Email 18 goes to both and alert A1 to the admin. It is an alert, not a row in `disputes` (REPLACEMENT_PLAN 2.7). The brand can then record again. A confirmed or disputed record cannot be decided again (`409 DIRECT_PAYMENT_NOT_PENDING`).
- **Database rules:** not both confirmed and disputed; `confirmed_by` set exactly when `confirmed_at` is; `dispute_reason` set exactly when `disputed_at` is.
- **Privacy:** the UPI ID is masked everywhere else: the deal detail's `directPayments[]`, the creator's own views, documents, the report, emails, deal events and logs. It is never in `deal_events` metadata or an email body.

### 7.4 Invoices

- **ValueSkins fee invoice** (identifier and URL slug `commission-invoice`), issued by Valueskins Private Limited to the brand when Payment 1 is captured. Number `VS/2026-27/000001`. Contents: ValueSkins legal name, address, GSTIN (when it has one), SAC code, brand billing name, address, state and GSTIN if any, place of supply (the brand's billing state), taxable value, tax, total, Razorpay payment id, date. **[CONFIRM format with the CA before go-live.]**
  - With GST charged, the document is titled "Tax Invoice" and splits the GST into CGST + SGST when the brand's billing state is the company's state (`COMPANY_STATE`), or IGST when it is not. The two states are compared as text, ignoring case and spacing, so a misspelled state is billed as IGST. The odd paisa of an odd GST amount goes to SGST so the halves add up.
  - With GST 0 (a test environment: GST is charged by default, section 4.2) the document is titled "Invoice" and has no tax lines. The amounts always come from the deal's frozen breakdown, never from today's rate.
- **Advance payment record** and **Final payment record** (REPLACEMENT_PLAN 2.1): issued when the creator confirms a direct payment. They are not receipts and not GST documents. They say: "Paid directly by the brand to the creator by UPI. ValueSkins did not receive or hold this money." Contents: the creator's name on the account, username, Instagram user id and masked UPI ID, the brand's billing name, the amount, the UPI reference and note, the time the brand recorded it and the time the creator confirmed it. Both stages share one gapless series, `VS-PR/2026-27/000001`, `000002`, and so on.
- The invoice line reads "ValueSkins fee for the deal <short id>" on invoices issued from Prompt 17 on. Invoices issued earlier keep the wording stored in their snapshot, which re-renders unchanged. Tell the CA about the new line.
- Tax invoices and payment records are numbered in separate gapless sequences per financial year (April to March, in IST). One upsert on the counter row (`invoice_counters`) takes its lock and holds it until the transaction that issues the invoice ends, so concurrent captures queue up and a rollback leaves no hole. The payment record sequence is the `ADVANCE_PAYMENT_RECORD` counter row; `FINAL_PAYMENT_RECORD` uses the same one.
- The commission invoice is issued inside the transaction that marks its payment captured (section 7.3), once per payment (unique on `payment_id`; a payment recorded on a deal that cannot take it gets none). A payment record is issued inside the transaction that confirms its direct payment (section 7.3a), once per direct payment (unique on `direct_payment_id`). An invoice row belongs to exactly one of the two.
- The invoice number and a JSON snapshot of all its data (company details from env at that moment included) are stored in `invoices` when issued, so re-rendering later always produces the same document, byte for byte. PDFs are rendered on demand with PDFKit and never stored, in an embedded DejaVu Sans font (the built-in fonts have no rupee sign), plain black on white.
- Each document is downloaded from `GET /deals/:id/documents/:kind` (section 16) by the deal's brand, its confirmed creator or an admin, once its payment is captured; the deal record (kind `adp`) only when the deal is COMPLETED. The deal's `documents` list (section 16) gives the number and date of each one that exists. They are also attached to emails 4 (brand), 5, 9 and 10 (section 8).

## 8. Emails

Sent through Resend from `ValueSkins <notifications@valueskins.com>`, reply-to `SUPPORT_EMAIL`. Every email ends with the line "Questions? Write to <SUPPORT_EMAIL>." (text and HTML), added in one place when the email is logged and sent, so it is in the stored text and in an admin resend, and never doubled. ## 10. Real-time (Socket.io)

Socket.io runs on the API's own HTTP server (`apps/api/src/realtime/`), on the same origin as the REST API (`api.valueskins.com`), path `/socket.io`, CORS origin `WEB_ORIGIN` with credentials. A socket only says that something changed: **clients refetch over REST on every event, on load and on reconnect. Sockets are never the source of truth**, and no payload carries anything REST would hide (no UPI ID, email or payment details).

**Handshake.** Socket.io answers `/socket.io/*` before Express, so the Express checks do not apply and the socket code does its own:

- If the request has an `Origin` header and it is not `WEB_ORIGIN`, it is refused (HTTP 403). Browsers always send Origin; a non-browser client sends none and still needs a session.
- The session cookie (`SESSION_COOKIE_NAME`) must be present and valid, checked like any request (`findValidSession`). A missing, malformed, unknown, expired or deleted session is refused: the client gets `connect_error` with the message `unauthorized`. The handshake does not extend the session or touch `last_active_at`.
- Handshake headers and cookies are never logged. A connection logs only the socket id, the user id and the transport; a refusal logs a reason word.

**Rooms.**

| Room            | Who is in it                                                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `user:<userId>` | The user's own sockets, joined on connect. The id comes from the session.                                                                                                                        |
| `feed:creators` | Joined on connect by a user whose role is CREATOR and who finished onboarding (the rule of `GET /deals/feed`). Never a brand, an admin, an unfinished creator or an account with no role.        |
| `deal:<dealId>` | Joined on request, only by the deal's brand, its confirmed creator, or an admin (`loadParticipantDeal`: a creator who merely applied is not allowed, even to an OPEN deal that REST shows them). |

A client joins with `deal:join` `{ dealId }` and leaves with `deal:leave` `{ dealId }`. Both answer through the acknowledgement callback with `{ ok: true }` or `{ ok: false }`. A refusal never says why, so a stranger cannot tell a deal that does not exist from one they may not join. A bad payload (anything but `{ dealId: <uuid> }`), more than 50 deal rooms on one socket, or more than 30 `deal:join` calls a minute on one socket is `{ ok: false }`. The session is checked again on every join; if it is gone the answer is `{ ok: false }` and the socket is disconnected. A client rejoins its deal rooms after a reconnect (rooms do not survive one). Messages are limited to 10 kB.

**Events.** Sent only after the database commit, and a failure to send is logged and never fails the request. Names, room builders and payload schemas are in `packages/shared/src/realtime.ts`.

| Event             | To                                      | When                                                                                                                                                                                                                                                               | Payload                                                                                                                                                                               |
| ----------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `deal:new`        | `feed:creators`                         | A draft is published (DRAFT to OPEN)                                                                                                                                                                                                                               | `{ id, title, brand: { username, profilePictureUrl }, budgetPaise, creatorAmountPaise, applicationDeadline, contentUploadDeadline }`, built from this list, never from the whole deal |
| `deal:closed`     | `feed:creators`                         | A deal leaves OPEN (confirmed or cancelled), so it drops out of feeds                                                                                                                                                                                              | `{ id, status }`                                                                                                                                                                      |
| `deal:updated`    | `deal:<id>`                             | Every deal transition (one event per transition, whichever route or webhook caused it), and also when a direct payment is recorded or marked not received, and when a dispute is raised or resolved (the status is unchanged, but the deal page has something new) | `{ id, status }`                                                                                                                                                                      |
| `application:new` | `user:<brandId>`                        | A creator applies                                                                                                                                                                                                                                                  | `{ dealId, applicationId }`                                                                                                                                                           |
| `deal:summary`    | `user:<brandId>` and `user:<creatorId>` | Every deal transition, a direct payment recorded or marked not received, and a fee kept on a changed deal, so the two parties' lists re-read                                                                                                                       | `{ id, status }`                                                                                                                                                                      |

The picture key is `profilePictureUrl`, the same as in the REST feed. Transitions send their events from `transitionDeal`, once, right after the commit and before the email tasks (a lost race, a failed step or an invalid pair sends nothing). The direct payment confirm is a transition. Applying, recording a payment, marking it not received, raising a dispute and resolving one are not, so those services send their own: the direct payments service and the fee capture call `emitDealChanged` (`deal:updated` plus `deal:summary`), the disputes service calls `emitDealUpdated`, and an architecture test lists the callers. A refused raise (a second open dispute, a stranger) sends nothing. The payload never carries the dispute text.

**The web client** (`apps/web/components/realtime/RealtimeProvider.tsx`) connects once the user is signed in and onboarded, joins the room of the deal page it shows (and joins it again after every reconnect), and re-reads over REST on every event, on reconnect and on window focus. Lists such as Campaigns, My deals and Applications do not join deal rooms (the join limit): they re-read on `deal:summary`, which reaches both parties in their own room, plus `application:new` for the brand, on focus and on reconnect. Admin pages connect too: an admin may join any deal room, and the admin deal page joins its own, so it updates live.

**Not covered (a client refetches instead):** a creator picked or passed over for a deal (they refetch `GET /applications/mine` on `deal:closed` and on reconnect); drafts (nobody else sees them); refunds (they are done by hand outside the API); a session that is logged out while a socket is open (the next `deal:join` notices, and events carry only ids and statuses).

**One instance.** Single Render instance for v1 (the emitter is in memory). Scaling to more than one instance later needs the Socket.io Redis adapter and sticky sessions, and a transition handled by one instance would otherwise not reach sockets held by another.

## 11. Virtual resume (hover card)

On hover (desktop) or tap (touch) over any username or avatar. Endpoint `GET /api/users/:id/resume` (by user id, not username), for signed-in users, cached in the API process for 5 minutes (`Cache-Control: private, max-age=300`, so a profile saved just now, or an age that has just risen, shows after the cache expires). It returns `{ user, stats, completedDeals }`:

- `user`: `id`, `role`, `username` (the Instagram handle and, in the UI, its link), `name` (the name the user gave once the profile is locked), `profilePictureUrl`, `instagramVerified`, `igAccountType` (the account type, `BUSINESS` or `MEDIA_CREATOR`), `followersCount`, `engagementRate`, and from the locked profile `city`, `age` (the **current** age, section 6.4), `gender`, `website`, `pitch` (each null until the profile is saved), the verified **`contactEmail`** (there is no chat, so the two sides write to each other, REPLACEMENT_PLAN 2.5; null if the email is not verified) and `memberSince` (when the account was created).
- `stats`: `completedDealsCount` and `totalValuePaise`, over every completed deal of the user, not only the last 10.
- `completedDeals`: the last 10 completed deals, `{ counterparty: { id, username }, budgetPaise, title, completedAt }`, the most recent first; a deleted counterparty shows as "Deleted user".

Unknown, deleted and role-less users (an email-only account that has not connected Instagram) are a 404. **Decided:** the resume shows the contact email and the deal amounts to every signed-in user, as on the live site.

## 12. Disputes and admin

- **Raise dispute** (`POST /deals/:id/disputes`) on any deal that has a confirmed creator and is past OPEN (CONFIRMED to COMPLETED, and a CANCELLED deal that had a creator), for its brand and its confirmed creator only (everyone else, admins included, gets 404; `409 DISPUTE_NOT_ALLOWED` before that). Body: subject (1 to 150 characters), description (1 to 5000). Creates a `disputes` row and sends Email 15 to `DISPUTE_EMAIL` with both parties in CC. 3 per deal per 24 hours per user (section 13). A deal can have several disputes over time, but only **one open at a time**: a second raise answers `409 DISPUTE_ALREADY_OPEN` ("A dispute is already open on this deal"), checked before the rate limit is used, and a partial unique index (`disputes_one_open_per_deal_idx`, one `OPEN` row per deal) makes two simultaneous raises safe (the loser gets the same 409). The deal's actions list `RAISE_DISPUTE` when it is allowed, disabled with that reason while a dispute is open. Raising a dispute sends `deal:updated` to the deal room. The deal detail lists the deal's disputes to its two parties (section 16), without the text or the resolution.
- Admins are users whose Instagram user id is in env `ADMIN_INSTAGRAM_USER_IDS`. `is_admin` is set on login from that list.
- `/admin` (admin only, 404 for everyone else):
  - **Analytics** (auto-refresh every 30 seconds):
    - All time: deals created, deals completed, active creators, active brands, total value transacted.
    - This week: deals created, completed, average deal value, average time from OPEN to COMPLETED.
    - This month: deals created, completed, commission revenue (base, excluding GST), creator payouts, completion rate.
    - Charts: deals by status, daily deals created (30 days), daily commission revenue (30 days), histogram of hours from a direct payment being recorded to the creator confirming it.
    - Tables: recent deals, recent direct payments, open disputes. Every row links to a detail view.
  - **Deal list** (`GET /admin/deals?status=&q=&limit=&cursor=`): every deal including drafts, newest first, filtered by status and searched by short id (prefix, any case). Each item has the summary, the creator and four more fields: `hasOpenDispute` (a dispute on the deal is open), `awaitingConfirmation` (a recorded direct payment for the stage that is due waits for the creator, the rule the confirm reminder uses), `contentOverdue` (from the deal's dates and the clock, never stored) and `updatedAt`. The response also has `total`: every deal that matches the status and search filters, not only this page, the same on every page.
  - **Deal detail** (`GET /admin/deals/:id`): full event log (each event has `kind`, `actor.role` and `refundReference`, section 15), payments (with the invoice number each produced), direct payments (every record, disputed ones too, with the UPI ID masked), emails (with recipient addresses, their stored `bodyText` and the 200 newest; a UPI ID is in no template, so none is in a body), disputes (the full admin view below). A deleted user is "Deleted user" everywhere in it, never the anonymized username. It also has `parties` (`{ brand, creator }`, each party with their `email`, null for a deleted account; admins only, the deal itself carries no address) and `adminActions` (`[{ action, enabled, reason }]` for `CANCEL` and `RESEND_EMAIL`, from shared `computeAdminDealActions`: cancel is enabled from COMMISSION_PAID to APPROVED, otherwise disabled with "This deal is already cancelled" or `ADMIN_CANCEL_WINDOW`; resend is disabled with "No emails on this deal yet"). Admins get no `allowedActions` of their own on the deal, which they read as a non-party. Actions: cancel deal (`POST /admin/deals/:id/cancel`, admin override from COMMISSION_PAID to APPROVED, section 5.2: requires a resolution note, optional manual refund reference, sends email 11). A deal outside that window answers `409 INVALID_TRANSITION` with the plain message "An admin can cancel a deal after the fee is paid and before it is completed." The refund reference is stored as its own field on the deal event (`refundReference`, not text in the note), resend any email. There is no transfer to retry: the advance and final are paid by the brand directly (section 7.3a).
  - **Resend** (`POST /admin/emails/:id/resend`): sends the stored subject and text again to the stored address and CC list as a new `email_log` row (the original stays). Only the plain text is stored, so the HTML is rebuilt from it. Invoices, payment records and the deal record that the first email carried are rebuilt from their stored snapshots (the deal record from the database as it is now, under the current file name); an attachment that cannot be rebuilt is left off and named in `missingAttachments`.
  - **Disputes** (`GET /admin/disputes?status=`, `GET /admin/disputes/:id`, `POST /admin/disputes/:id/resolve`): list (with `total`, every dispute with the status filter, not only the page), one dispute (with `deal`, the deal's status, parties, amounts and paid, confirmed and due dates, and `otherDisputes`, so the dispute page needs no second request), mark resolved with a resolution note and an optional refund reference (a second resolve is `409 DISPUTE_ALREADY_RESOLVED`). Email 15b goes to both parties. Resolving does not change the deal (it sends `deal:updated`); cancelling it is a separate action. The admin view of a dispute (`DisputeView`) has `raisedBy` `{ id, username, role }` (`BRAND` or `CREATOR`, from the deal's parties) and, once resolved, `resolvedBy` `{ id, username }` (null while open). A deleted raiser or resolver shows as "Deleted user". An unknown id, or anyone who is not an admin, gets 404.
  - Every admin route answers 404 to signed-out users and non-admins alike. The admin screens are built (section 18). The analytics (`GET /admin/analytics`, and the analytics screen) are not built yet: there is no endpoint and no design for them.
- Refunds, when needed, are done manually in the Razorpay dashboard. The admin records the refund id in the resolution. No automated refunds in v1.

## 14. Scheduled jobs

All run in the API process via `node-cron` (`apps/api/src/jobs/`), in `Asia/Kolkata` time. They start in `src/index.ts` after the server listens and stop first on SIGTERM (a running job finishes before the database closes); `createApp` never starts them, so tests do not. Each run:

- takes a Postgres advisory lock named `job:<name>` on a dedicated connection (`pg_try_advisory_lock`). A run that finds it taken does nothing and is logged as `skipped`: it never queues. This keeps a redeploy overlap, a second instance, or a run started by hand from double-running a job. The lock is released in `finally`, and a process that dies drops its connection, which frees it.
- logs one line: `{ job, status: ok | skipped | failed, durationMs, ...counts }`. A job that throws is logged with the error, reported as `failed`, and never crashes the process. Count names avoid the words the logger redacts (`token`, `code`, `account`, `pan`). No email address, token or UPI ID is logged. A failed run is not emailed.
- can be run once by hand: `pnpm job <name>` (or `pnpm job --list`), from `dist` as `pnpm --filter @valueskins/api run job:deploy -- <name>` on Render. It uses the real clock and the same lock, and exits 1 on failure.

## 15. Database schema

Conventions: UUID v7 primary keys, `created_at`/`updated_at` `timestamptz` default now, money columns `_paise BIGINT`, enums as Postgres enums. Foreign keys everywhere, with indexes on every foreign key and every column used in a filter (a test, `test/db/indexes.test.ts`, checks that every foreign key has one).

**Indexes on `deals`** (migration 0011, found with EXPLAIN on a 50,000-deal database, `apps/api/scripts/explain-seed.ts` and `explain-queries.ts`): `(brand_id, id desc)` and `(creator_id, id desc)` for my deals, the resume and applicants; `(status, id desc)` for the admin list and the job scans; a partial `(published_at desc, id desc) where status = 'OPEN'` for the creators feed; `varchar_pattern_ops` on `short_id` for the admin prefix search (`LIKE 'AB1%'` cannot use the unique index; it scanned the whole table before: 9 ms became 0.2 ms at 50,000 deals). They replace the single-column `brand_id`, `creator_id` and `status` indexes, whose first column they keep. The unfiltered admin `total` is a count over the smallest index (about 7 ms at 50,000 deals) and grows with the table; if it matters later, use an estimate.

**users**

**brand_billing** (1:1 users)
`user_id (pk), billing_name, billing_address, billing_state, gstin (nullable), created_at, updated_at`

**sessions**

**email_verification_tokens**

`id, deal_id, link, uploaded_at`

**invoices**
`id, deal_id, payment_id (nullable), direct_payment_id (nullable), kind (COMMISSION_TAX_INVOICE | ADVANCE_PAYMENT_RECORD | FINAL_PAYMENT_RECORD), number (unique), financial_year, sequence, snapshot jsonb, issued_at`
Exactly one of `payment_id` (the commission invoice) and `direct_payment_id` (a payment record) is set, each unique. Numbering uses a row lock on a per-financial-year counter table (`invoice_counters`), so numbers are gapless and never duplicated. The tax invoice has its own counter; advance and final payment records share the `ADVANCE_PAYMENT_RECORD` row (section 7.4).

**deal_events**
`id, deal_id, from_status, to_status, actor_id (nullable), actor_type (USER | SYSTEM | ADMIN), note, metadata jsonb, created_at`
Two writers, and nothing else (an architecture test checks it; the seed inserts its own): `transitionDeal` writes a row for every status change, and the payment record helper (`deals/dealEvents.ts`) writes one for a direct payment that was recorded or marked not received, in the same transaction as that change, so a failed write leaves neither. A payment event moves nothing, so `from_status` and `to_status` are both the status the deal was in. Its `metadata` is `{ kind: 'PAYMENT_RECORDED' | 'PAYMENT_NOT_RECEIVED', directPaymentId, stage }`: ids only, never the UPI ID or the reference. A not-received event's `note` is the creator's reason. The same helper file writes the event for a fee captured on a deal that had changed (section 7.3): actor SYSTEM, `metadata` `{ kind: 'FEE_CAPTURED_DEAL_CHANGED', paymentId }`, no note. An admin cancel stores `{ adminCancel: true, refundReference }` in `metadata`, and its `note` is the plain resolution note.

**Event view** (`GET /deals/:id/events` and the admin deal detail share it): `{ id, kind, fromStatus, toStatus, actor: { type, role, username }, note, refundReference, createdAt }`. `kind` is `TRANSITION`, `PAYMENT_RECORDED` or `PAYMENT_NOT_RECEIVED`. `actor.role` is `BRAND`, `CREATOR`, `ADMIN` or `SYSTEM`: a user who acted is the deal's brand or its confirmed creator (otherwise their account role); it is null only for an actor with no role. A deleted actor's `username` is "Deleted user". `refundReference` is read from the metadata, null when none was given.

**email_log**
`id, deal_id (nullable), user_id (nullable), to_email, cc jsonb, template, subject, body_text, attachment_names jsonb, provider_message_id, status (QUEUED | SENT | FAILED), error, created_at, sent_at`

**disputes**
`id, deal_id, raised_by_id, subject, description, status (OPEN | RESOLVED), resolution, refund_reference, resolved_by_id, resolved_at, created_at`
Unique partial index `disputes_one_open_per_deal_idx` on `(deal_id)` where `status = 'OPEN'`: one open dispute per deal (migration 0010 first resolves any extra open ones, keeping the newest).

**webhook_events**
`id (Razorpay event id, pk), event_type, payload jsonb, received_at, processed_at, error`

**meta_deletion_requests**
`id, instagram_user_id, confirmation_code (unique), status, created_at, completed_at`

User deletion: soft delete (`deleted_at`), anonymize username, email and Instagram fields, delete tokens and sessions, and delete a brand's `brand_billing` row. Deals, payments and invoices are kept (legal record) but show "Deleted user". Every invoice and payment record keeps the billing it was issued with in its snapshot, and the deal record reads the brand's billing from the fee invoice's snapshot (falling back to the live row only for a deal paid before invoicing shipped), so documents re-render the same after a deletion.

## 17. Deal record (ADP) contents

Generated on demand with PDFKit, same document for both parties.

1. Header: "ValueSkins Deal Record", deal short id, generated timestamp (IST). The file is `ValueSkins-Deal-Record-<short id>.pdf` and email 10 is "Deal record ready".
2. Parties: brand and creator Instagram usernames and Instagram user ids, brand billing name and GSTIN if any.
3. Terms: title, full description, budget, the three deadlines, published and confirmed dates.
4. Money: budget, ValueSkins fee base, GST, ValueSkins fee total, creator amount, advance, final.
5. ValueSkins fee tax invoice (full).
6. Advance payment record (full).
7. Final payment record (full).
8. Delivery proof: every content link uploaded with its timestamp, number of revisions, each feedback timestamp, final approval timestamp.
9. Direct payments: every record for the advance and final, disputed and waiting ones included, with stage, amount, UPI reference, masked payee UPI ID, recorded time and its status (confirmed time, or not received with the reason).
10. Razorpay fees absorbed by ValueSkins (from the ValueSkins fee payment's Razorpay entity, stored on `payments` when captured; "Not recorded" for older rows), for information. Only the commission goes through Razorpay.
11. Event timeline from `deal_events`: a status change reads "CONFIRMED to COMMISSION_PAID", a recorded or not-received payment reads "Payment recorded (advance)" or "Payment marked not received (final)" (never "X to X"), and an admin cancel's refund reference is printed on its own line as "Refund reference: ...". A deleted user is "Deleted user".

## 18. UI and copy

The whole web app uses one design system, taken from the home page, the approved look. The tokens live in `apps/web/app/styles/tokens.css` (colours with semantic roles, type, spacing, radii, shadows and motion); the Tailwind theme (`apps/web/tailwind.config.ts`) maps every colour, size, radius, shadow and duration to the same CSS variables; the component classes are in `apps/web/app/styles/` (`base.css`, `components.css`, `shell.css`, `screens.css`). The home page's own styles (`apps/web/app/landing.css`, scoped under `.v3`) use the same tokens. The old "Receipt" design (`docs/design/receipt.css`, `docs/DESIGN_HANDOFF.md`) is superseded and no screen uses it. `/dev/components` (non-production builds only, the same gate as `/dev/login`) shows every shared component in every state.

- **Look.** Light only, with no dark mode. A warm off-white ground `#FBF8F4`, white cards with a 1px warm rule and a soft shadow, ink `#1A1612` (muted `#5C534B`, helper `#6E645A`), and near-black `#100D0B` contrast sections on the public pages. Saffron is the one accent: `#C2410C` on light grounds (`#9A3412` as text on its tint) and `#FF7A3D` on dark, used for the primary action, the 3px focus ring, the current step and key money moments. Status colours carry meaning only: success, warning, danger, info, each with a soft tint. Every text pairing is AA (4.5:1; 3:1 for input edges and focus rings). Buttons, badges, chips and tabs are pills; inputs 14px radius; cards 18px; modals and sheets 24px. App screens are calmer than the home page: content first, no glows or tilts.
- **Type.** Bricolage Grotesque for headlines, UI and text, and Instrument Serif italic for one accent word, used sparingly (the wordmark "Value" + "Skins", a welcome headline), both self-hosted with `next/font`. Money and counts use tabular figures; ids, UTRs and UPI IDs use the system monospace. Scale: display 40/44, h1 28/34, h2 22/28, h3 18/24, body 16/24, small 14/20, label 12/16.
- **Motion.** Transform and opacity only, with feedback rather than decoration: buttons press in, menus, popovers, modals and toasts rise in, a deal status badge pops when it changes live (not on first render), progress bars fill, and newly mounted list rows and cards rise in gently, so rows that arrive with a realtime update animate and the rest stay put. Under `prefers-reduced-motion` nothing animates.
- **Touch.** Every control is at least 44px tall on phones and touch screens.
- **Icons.** Phosphor, regular weight, drawn inline with `fill: currentColor`, the one set the home page and the app share. Every icon-only button has a name.
- **Copy.** CLAUDE.md section 12 applies to the web too: short sentences, no emojis, no em or en dashes, none of the banned words. Button labels start with a verb.
- Every amount is shown as `₹10,000.00` (Indian digit grouping, `en-IN`), with the paise a shade lighter in large amounts. Dates look like `30 Sep 2026`, times like `9:12 am`, always IST.
- **Homepage** (`/`, `apps/web/app/(landing)`, `apps/web/components/landing`, styles in `apps/web/app/landing.css` scoped under `.v3`, on the app's tokens). The bolder version of the look: one accent word in Instrument Serif italic per headline, rose `#F7B7C3` and sand `#FFF4EC` as warm second tones, pill labels, glass panels and blurred glows.
  - It has its own navigation (wordmark; For brands, For creators, How it works and FAQ, folded into a Menu button on phones; and a compact Sign in). Its dark footer is the one every public page uses (`SiteFooter`: How it works, Terms, Privacy, Refunds, Contact, the support address from `GET /config` with `founder@valueskins.com` until it answers, and the © Valueskins Private Limited line). Its database is a **Neon** project, not a Render database, so `DATABASE_URL` is a prompted variable. The API there is deployed by hand, and the values that change after launch (`DATABASE_URL`, `HOSTING_TIER`, `PAYMENTS_MODE`, `DEAL_POSTING_MODE`, `ADMIN_INSTAGRAM_USER_IDS`, `WEB_ORIGIN`) are prompted variables owned by the dashboard, so a Blueprint sync never resets them. Every production value and who provides it is in `docs/DEPLOYMENT.md` section 21.

**Hosting tier.** `HOSTING_TIER` is `free` or `paid` (blank or unset means `free`). Production starts on free hosting: the API on Render's free instance type, which sleeps after 15 minutes without traffic (about a minute to wake), has no pre-deploy command and no Shell, and runs the scheduled jobs only while it is awake, and the database on Neon's Free plan (scale to zero after 5 minutes, restore window 6 hours). A startup guard refuses `PAYMENTS_MODE` or `DEAL_POSTING_MODE` set to `on` in production unless `HOSTING_TIER=paid`; `off` and `admins` are allowed on free hosting, so the founders can test with real admin accounts. Everything else about the payment checks is unchanged: `PAYMENTS_MODE=admins` still needs the live Razorpay values and `COMPANY_GSTIN`. While the API is asleep, reminders and scheduled jobs do not run, and a test deal that is left open is visible to every creator, so every test deal must be cancelled or completed before the cutover switch (`docs/CUTOVER.md` section C). Moving to paid (`docs/DEPLOYMENT.md` section 21.9) comes before either gate opens to everyone (`on`).

**The database connection.** The pool has at most 5 connections and waits at most 30 seconds for one, and a failed idle connection is logged, not fatal (Neon drops idle connections when its compute suspends). Two startup guards check `DATABASE_URL` without connecting: a host containing `-pooler` is refused in every environment (a pooled Neon connection runs PgBouncer in transaction mode, where the session-level advisory locks of the jobs and the migrations do not work, so the direct string is required), and production requires `sslmode=require` (or `verify-ca` or `verify-full`).

**Migrations and the startup check.** Migrations never run on start or in the build. Production is migrated by hand, from a person's machine, with `DATABASE_URL` read from the shell and never written to a file (`pnpm db:migrate`, `docs/DEPLOYMENT.md` section 21.4), before each deploy that adds a migration. Before it listens, the API connects and compares the migrations the database has applied with the ones in the code, by hash. If the code has migrations the database has not applied, it logs which ones, by name, and exits with code 1: the schema would be missing a change. If the database has migrations the code does not know (it is ahead, for example after a migration was run before the deploy, or after a rollback), it logs a warning naming them, by hash and time, and starts: migrations are written so the previous code keeps working, so a rollback past a migration is safe. If it cannot connect, it logs the host and a reason taken from the error code, never the connection string.

Web env: `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_SENTRY_DSN`, plus `NEXT_PUBLIC_ENABLE_DEV_LOGIN` (staging only, never set in production). On staging they are Vercel project variables. In production they are GitHub Actions variables, read by the `deploy-web-production` workflow, which also holds the secrets `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID`; the Netlify site itself has no variables. The workflow runs only after CI passes on a push to `main`, never for a pull request or a fork, deploys only when the merge changed something the web build uses, and refuses a `NEXT_PUBLIC_API_URL` other than `https://api.valueskins.com`. The Netlify Free plan has 300 credits a month and a production deploy costs 15 (`docs/DEPLOYMENT.md` section 21.6). There is no Razorpay variable on the web: Checkout uses the `keyId` the fee order returns, which always matches the server's key. `next build` always runs with `NODE_ENV=production`, so the web dev login page is gated by `NEXT_PUBLIC_ENABLE_DEV_LOGIN=true` instead, and a build with that flag true and `NEXT_PUBLIC_API_URL` set to `https://api.valueskins.com` fails. Whether "Sign in with email" shows comes from `GET /api/config` (`authEmailEnabled`), not from a web variable. A build whose `NEXT_PUBLIC_API_URL` is the production API leaves out the "Not in this version" notes on the legal pages (section 18).

Staging runs on Render's free Postgres plan: it expires 30 days after creation and has no backups. Production must use a paid plan with backups (section 2). Setup steps are in `docs/DEPLOYMENT.md`.

## 20. Security checklist

- Secrets only in env, never in the repo. `.env.example` lists names only.
- Never log tokens, secrets, email bodies, PAN, bank numbers, or full webhook payloads at info level.
- Webhook signature always verified on the raw body. Meta signed requests always verified.
- Every endpoint checks ownership (brand of this deal, confirmed creator, admin). Tested.
- Helmet security headers on the API. A nonce-based CSP on the web app that allows Razorpay Checkout, and Sentry only as the exact host of its DSN, as third parties (section 18).
- **Error reporting (Sentry, errors only).** On only when `SENTRY_DSN` (API) or `NEXT_PUBLIC_SENTRY_DSN` (web) is set. No tracing, replay, logs or breadcrumbs. Before an event is sent (`scrubSentryEvent` in `packages/shared/src/scrub.ts`) the user and so the IP, the server name, request headers, cookies, bodies and query strings, breadcrumbs and stack variables are removed, and every remaining string has emails, UPI IDs, bank-account-shaped numbers (9 to 18 digits), PAN and IFSC shapes, bearer tokens and `code=`/`token=`/`state=` values replaced. The API reports only unexpected errors: a 5xx (`errorMiddleware`), an uncaught exception or rejection, a failed job, a failed webhook processing, and the after-commit steps that are logged and swallowed (emails, documents, realtime); a 4xx the caller caused is never sent. `src/instrument.ts` starts it before anything else loads.
- **Logs use the same scrubber.** `deepRedact` in `apps/api/src/logging/logger.ts` is `scrubValue`: an Error is kept as its name, scrubbed message and scrubbed stack (it was lost before), emails and UPI IDs are removed wherever they sit in a string, and keys that name a secret are redacted at any depth. A request is logged as its id, method, path (no query string), status and time; never headers, cookies, the client address or a body.
- **Route audit.** `apps/api/test/security/routeGuards.test.ts` walks every route the running app registers and fails when one has no auth guard and is not on its explicit public allowlist, when a guard or limiter changes without the expected table being updated, when a route is not behind the global rate limiter, or when a mutating route accepts a wrong Origin.
- Google Drive links are rendered as plain external links with `rel="noopener noreferrer"`, never embedded.
- Admin routes return 404 to non-admins.
- Dependabot enabled. `pnpm audit --prod --audit-level critical` in CI blocks on a critical advisory in what ships; the full `pnpm audit` is reported without blocking (the accepted dev-only ones are in `docs/RUNBOOK.md`).
